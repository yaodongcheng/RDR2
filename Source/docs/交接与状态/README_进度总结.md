## 4. L0：世界地图（真地形 + 官方区划）

### 4.1 真地形 —— 从**游戏地形瓦片**重建

```
levels_*.rpf → levels/rdr3/terrain/<area>/<letter>_<row>_.rpf    480 个瓦片包
   └─ 64 × <letter>_<row>__hd_0_<i>_<j>.ydr    本地 64m×64m / 17×17 顶点 / stride 56

世界坐标 = <letter>_<row>__strm_0.ymap 里 joaat(patch 名) 对应实体的 position
           x0,y0 = patch 中心（i,j 每 +1 → 各 +64 m）
           z0    = ★ 该 patch 的绝对基准高程
世界高程 = z0 + ydr 本地顶点 z
```

| 项 | 值 |
|---|---|
| 抽取 | **30,697 个地形 patch**（= 全集，已用放宽关键词重抽验证过没有遗漏）|
| 世界范围 | x[−7684,4612] y[−8196,4100]（与官方世界边界完全吻合）|
| 高程 | −79.7 ~ **728.5 m**（= 官方世界最高点）|
| 校验 | 12 个城镇对拍：**RMSE 15 m，中位误差 3.1 m** |

⚠️ **必须先讲清的历史更正**：`common_0.rpf` 里的 `heightmap.dat` **不是世界地形**。
判据：把官方水体多边形投到它上面，水/陆在 8 种朝向下**零相关**（水体高程百分位 26~58%，随机=50%），
缩放+平移全搜也救不回来。**别再拿它当高程用。**

### 4.2 官方区划

`common_0.rpf → data/levels/rdr3/mapzones.meta`（515 KB **XML**）→ **87 个 zone**：
9 州 + 19 地区 + 16 区 + 8 镇 + 34 水体，含多边形与 BoundBox。
陆地 = STATE 并集，水体 = 35 个官方水体多边形，栅格化成底图贴图（与地形同 extent 逐像素对齐）。

## 5. L1 / L2：据点

### 5.1 ★ 取据点的正确姿势：**空间聚类，不是文件名前缀**

反例：安尼斯堡按 `ann_*.ymap` 前缀只能捞到 632 个实体、命中 **4** 个建筑；
改成"中心 230 m 内的**全部** ymap 实体"后捞到 3545 个、命中 **219** 个。
（安尼斯堡的建筑被几十个**哈希命名的 ymap** 分散引用。）

### 5.2 三个据点的产出

| 据点 | 模型/实例 | 顶点 | 贴图 | 包体 | 加载方式 |
|---|---|---|---|---|---|
| 瓦伦丁 val | 69 / 69 | 79.8 万 | 173 | 22.3 MB | 整包 |
| 安尼斯堡 ann | 150 / 151 | 184.6 万 | 199 | 42.1 MB | 整包 |
| 圣丹尼斯 sdn | 1774 / 1788 | 1565 万 | 1253 | 353 MB | **分块流式** |

**为什么圣丹尼斯要分块**：它是真·大城市（全量 **2247 万顶点 / 1818 万三角**，
单是 Hotel St. Louis 一个模型就 4.3 万三角，大量 0.02~0.06 m 级装饰细节），
全量打包约 **485 MB** —— 单文件 Web 查看器装不下。
（也试过 ydr 自带低 LOD：**area 包里只有 high，没有 med/low**，走不通。）

### 5.3 分块流式（游戏做法）

1. 按 **160 m 网格切成 30 块**，各块自带模型+实例
2. **共享贴图字典** `tex.js`（1253 张 / 29.3 MB）单独一份，各块引用不重复
3. 查看器每 12 帧：以**摄像机地面投影**为中心，**由近到远**加载，
   **预算 140 MB / 最多 14 块**；**超预算时踢掉"比候选更远"的块**（按距离换页）
4. 超出 `LOAD+260 m` 的块自动 `dispose`

实测：`tex.js` 379 ms、单块 0.2~0.4 s。

**修复记录（2026-10-16）**：用户反馈"没有随摄像机移动加载"。
根因：**预算满后新块永远加载不进来** —— 卸载判据 `KEEP = LOAD×1.7` 最大 1700 m，
而整城才 1200 m 宽 ⇒ **已加载的块永远在 KEEP 内、永远不卸载、预算永远占满** ⇒ 新块被 `break`。
修法：改成**按距离换页**（候选比"当前最远已加载块"更近时，踢掉最远的腾预算）+ 预算提到 140 MB / 最多 14 块。
复测：`✅ 已加载 18 块 / 可见 16 块`（修复前卡死在 8 块），无报错。

## 6. 工具链（`tools/`）

| 工具 | 作用 |
|---|---|
| `build_terrain_heightmap.py` | 30,697 个地形 patch → 世界高程图（幂等，有 H4.npy 缓存）|
| `parse_mapzones.py` | `mapzones.meta` → 官方区划 JSON |

| `build_town_hpatch.py` | 用**建筑底座**推局部地形校准场（精地形补丁）|
| `build_world_map.py` | 组装单文件查看器 + 量化打包 L2 |
| `world_map.template.html` | 查看器模板 |

**复现一个据点**（约 10 分钟）：
```bash
# 1) 抽该区模型（示例：圣丹尼斯）
rdr2rpf.exe extract "<游戏>/levels_2.rpf" work/sdn/models "levels/rdr3/area/nopq_15_18/new_com_03.rpf"
# 2) 导真模型
uv run python tools/export_town_l2.py --code sdn --cx 2555 --cy -1151 --r 620 \
    --ydr work/sdn/models --maxs 96 --weld 0.25 --chunk 160 --out work/sdn/town.json
# 3) 精地形补丁 + 组装
uv run python tools/build_town_hpatch.py --code sdn --town ... --out work/sdn/hpatch.json
uv run python tools/build_world_map.py
```

## 8. 关于"three.js 有压力，用 Blender 会不会更好"

会，而且**好得多**，但两者定位不同：

| | three.js 查看器 | Blender |
|---|---|---|
| 性能上限 | 受 WebGL / 浏览器内存限制（所以圣丹尼斯要分块流式）| 高一个数量级，2200 万三角轻松转 |
| 分发 | **双击即开、无需装软件** ✅ | 要装 Blender |
| 用途 | **交付给团队看** | **自己验收/编辑/调材质** |
| 数据格式 | 自定义 L2 包 | glTF / FBX + 贴图 |

**结论**：如果目的是"我自己流畅地看整个圣丹尼斯"，Blender 明显更合适 ——
我可以把据点导成 **glTF/FBX（含贴图）**，你在 Blender 里直接 fly 着看。
如果目的是"团队随手能打开"，就继续用现在的 three.js 分块流式。

（注：GLB 单体会很大（圣丹尼斯约 1 GB），Blender 导入需要等一会儿，但转起来是流畅的。）
