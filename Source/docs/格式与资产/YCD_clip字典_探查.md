# YCD（clip 字典）探查记录

> 目标：解出「clip 名 → 帧数/数据偏移」，从而给每个镜头挂上**时长**。
> 现状：**名字 → 字符串的指针链已打通**；帧数/时长字段仍未找到。
> 日期：2026-10-23

## 1. 已确认

### 1.1 文件结构

```
+0x00  RSC8 头 16 字节（magic=RSC8, val1, val2；wnt1_mcs1.ycd comp=None 未压缩）
+0x10  体：struct + 指针（0x50000000 基址的虚拟地址）
      结尾处是一张「clip 名 → 结构」的字典
```

### 1.2 clip 名以 **joaat 哈希** 为键

```python
joaat("cs_dutch_face_wnt1_mcs1_p1a1_t06_shot_1") == 0x2fd28bb7   # 在 .ycd 里命中
joaat("exportcamera_wnt1_mcs2_p2_t03_shot_1")    == 0x854c60c0   # 同样命中
```

> 之前搜 `0xdaf69198` 搜不到，是因为那个哈希不是名字哈希。**名字哈希 = joaat(小写 clip 名)**。

### 1.3 指针链（已走通两级）

以 `exportcamera_wnt1_mcs2_p2_t03_shot_1` 为例：

```
字典条目 @0x71860   { name_hash: 0x854c60c0, ptr: 0x500068b0 }
   ↓
结构 @0x68b0        { ..., +0x20: 1, +0x30: 2, +0x38: ptr 0x50061610 }
   ↓
结构 @0x61610       { +0x00: 0x00020002, +0x10 起是 ASCII "pack:/exportcamera_....clip" }
```

结论：**字典条目 → 结构 → 名字字符串** 可以稳定还原；
即「clip 名 ↔ 文件内位置」是可解的。

## 6. `.yad` 分页的结构性规律（本轮新发现）

同一分页内**所有动画时长完全一致**，且不同分页之间常出现 **D 与 2D 成对**：

| 过场 | 分页 | 每页动画数 | 页内时长 |
|---|---|---|---|
| `wnt1_mcs2` | 10 页 | 11~19 | 16.0 / 16.0 / 6.2 / 9.7 / 12.6 / 3.0 / 2.9 / 6.9 / 2.4 / 9.0 |
| `wnt1_mcs1` | 4 页 | 7~8 | 16.0 / (10.5·21.0·31.6) / 16.0 / (10.5·21.0) |
| `bou1_mcs1` | 13 页 | 6~10 | 5.1·10.2 / 3.3·6.6·30.0 / 8.1·16.2 / 16.0 / … |

含义（推断，未完全证实）：
- 一页更像「一次拍摄（take）」或「一个镜头」的素材集合，页内所有对象共用同一长度
- `D / 2D / 3D` 成对，像是「片段本身 + 整段 take + 全场景」三种粒度都存了一份
- 16.0 s 是分页上限，超过就被截断（这点已在 `shot_table.csv` 的 `dur_capped` 列标出）

**这条规律暂时不足以直接反推「第 N 镜多长」**：
用「去重后的基础时长个数 == 镜头数」去卡，16 个过场里只对上 5 个，相关性不够。

## 7. 又打通一段：clip 结构体哈希 ↔ `.yad` 分页（已证实）

`.ycd` 体里有一张 **32 字节步长**的根表（`wnt1_mcs2` @ `0x77cb0`，`wnt1_int_cabin` @ `0xa9d50`）：

```
{ ptr(8) | 0(4) | flags(4) | 0(4) | f32 | 0(8) }
  ptr → clip 结构体 {
        +0x08  u32 clip 哈希
        +0x28  f32 时长A
        +0x2c  f32 时长B（≈A×2）
        +0x30  f32 播放速率（1.0）
  }
```

**关键实测**：clip 结构体的 `+0x08` 哈希能在**唯一一个 `.yad` 分页**里命中：

| clip 哈希 | 时长A | 命中分页 |
|---|---|---|
| `0x947d666d` | 9.70 s | `wnt1_mcs2-3.yad` |
| `0xeda68025` | 12.63 s | `wnt1_mcs2-4.yad` |
| `0x7b669d58` | 9.00 s | `wnt1_mcs2-5.yad` |
| `0x6b8a25e1` | 20.30 s | `wnt1_mcs2-6.yad` |
| `0x72bf665f` | 36.00 s | `wnt1_mcs2-9.yad` |

`wnt1` 三个过场 **20/20 条 clip 全部落到具体分页**。

工具：`tools/extract_ycd_durations.py`（输出 `export/story/cutscene/ycd_durations/`）

## 8. 但「时长A」不能直接当镜头时长（重要更正）

拿到的时长里有超过整段过场长度的情况，例如：

| 过场 | 表里的时长 | 过场总长 |
|---|---|---|
| `wnt1_mcs2` | 52.8 / 27.87 / 27.0 / 19.4 … | 38.8 s |
| `wnt1_int_cabin` | 42.6 / 35.5 / 21.3 … | 28.4 s |

所以 `+0x28` 更像**累计时长/整段 take 长度**，不是「这一镜多少秒」。
**不能用它直接反推分镜时长**，否则会得出 52.8 s 的镜头这种荒谬结果。

下一步应当找表里与「分页内统一时长」对得上的那个字段（`.yad` 每页的动画时长是稳定的，
可以拿它当标尺去反查 `.ycd` 里哪个字段等于它）。

## 9. 「用分页时长当标尺」的结果（本轮验证完成）

拿 `.yad` 每页的统一时长去反查 `.ycd` clip 结构体，**每个 clip 都能在自己的结构里找到某个字段恰好等于所在页的时长**：

| clip 哈希 | 所在页 | 页时长 | 命中的字段偏移 |
|---|---|---|---|
| `0x947d666d` | `wnt1_mcs2-3` | 9.7 s | `+0x28` |
| `0xeda68025` | `wnt1_mcs2-4` | 12.6 s | `+0x28` |
| `0xb1570d28` | `wnt1_mcs2-3` | 9.7 s | `+0x2c` |
| `0x7b669d58` | `wnt1_mcs2-5` | 3.0 s | `+0x6c` |
| `0xf7242bb9` | `wnt1_mcs2-3` | 9.7 s | `+0x68` |

→ **「clip 时长 == 所在分页的时长」这条成立**（155/155 条 clip 都能对上）。

字段偏移在 `0x28 / 0x2c / 0x68 / 0x6c` 之间跳动，说明 `.ycd` 里 clip 结构体有几种变体（不同上下文的同一种结构），
但语义一致：**它们在描述「这一段的长度」**。

## 10. 但分页之间不是「顺序拼接」关系（重要）

把每页当一个镜头的话，时长加不起来：

| 过场 | 分页时长 | 求和 | 过场总长 |
|---|---|---|---|
| `wnt1_mcs2` | 16/16/6.2/9.7/12.6/3.0/2.9/6.9/2.4/9.0 | 85.7 s | **38.8 s** |
| `wnt1_mcs1` | 16/16/10.5/21.0/10.5/21.0 | 94.0 s | **31.6 s** |

**结论**：分页是**并列的候选素材（take / 不同镜头版本）**，不是一条时间轴。
游戏最终播哪几段、怎么排，由 `.yas` 场景或任务脚本决定 —— 这正是我们还没拿到的那层。

留一个观察（未定论）：`wnt1_mcs2` 去掉两页 16.0 封顶后，**剩下的页码数正好 8 = 镜头数**。
这条线索可能是「每镜一个 take 页 + 若干封顶页」，值得下一轮验证。
