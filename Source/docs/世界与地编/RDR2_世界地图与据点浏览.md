## 2. 本轮找到的三条关键事实（**别再重复踩**）

### 2.1 ❌❌ `heightmap.dat` **不是**世界地形（本轮推翻，别再拿它当高程）

**曾经的错误结论**：以为该文件是 768×768 的世界高度图（平铺 2×2 存满 1536²），并据此渲染"世界地形"。
**实际是错的**——那份数据渲染出来的"陆/水分布"和游戏完全不符（用户一眼看出"怎么那么多水域"）。

**判决性判据（可复现）**：把**官方水体多边形**（35 个 LAKE/RIVER/CREEK/POND/OCEAN/SWAMP）
投到该图上，看水体点是否落在地形低位：

```
水体点的平均高程百分位（越低越好；随机 = 50%）
  变体 ---: 33.9%   陆地 29.8%     变体 -YX: 26.0%   陆地 22.0%
  变体 --X: 58.2%   陆地 54.0%     变体 TYX: 26.0%   陆地 22.0%
  ... 8 种朝向全试：水体始终 **不低于** 陆地（最好的一档还比陆地更高）
再搜 缩放(0.7~1.5)×平移(±3km)：最佳"陆-水"落差仅 69.7 m，而地形自身 std = 127.9 m
```

⇒ **水/陆零相关**，任何仿射对齐都救不回来。这份 `heightmap.dat` 是某种别的东西
（不是世界高程），**不能当地形用**。

**后果链**：假地形 ⇒ 我用 `z=0` 水面去盖 ⇒ 大片沙漠（New Austin / Nuevo Paraiso 实际 −15~+100 m）
被淹成湖 ⇒ 与官方地图完全对不上。

**正解（本轮已改）**：底图**不再使用高程数据**，改为 **纯官方几何栅格化**（见 §3.1）。

### 2.3 ★ 相机必须做 RDR2 → three 坐标转换

场景根节点 `root` 绕 X 轴 −90°（RDR2 是 Z-up，three 是 Y-up）：
`RDR2(x,y,z) → three 空间 (x, z, −y)`。

**相机是加在 `scene` 上的，所以 `cam.position` / `controls.target` 必须先做这个转换**。
不转换的后果：

| 现象 | 原因 |
|---|---|
| 地图**上下颠倒**（Nuevo Paraiso 跑到顶部） | 站在"地下"看，成像是翻转的 |
| 近距离**整屏全黑**（远距离却正常） | 相机埋在地形下方，只能看到背面 ⇒ 被剔除 |

顺带还要修正**三角形绕序**（法线在 three 空间要朝上），否则地形只被半球光的"地面色"照亮 ⇒ 发黑。

## 4. ★ 怎么解决「一次加载太多模型会卡」

### 4.1 三层结构（LOD 式按需）

```
L0  世界总览（常驻，2.1 MB 单文件）
    ├─ **真地形网格**（1024² 顶点，分 16×16 块便于视锥剔除；高程来自 30,697 个游戏 patch）
    ├─ 官方底图贴图（陆地 + 官方水体 + 地区线 + 海岸线，2048px，与地形同 extent 逐像素对齐）
    ├─ 海面（z = −2.5 m，避开沼泽/三角洲的 0 m 斑驳）
    ├─ 官方区划矢量线：州界 / 地区界 + 名称标签（52 个 zone）
    └─ 据点 pin（130 个具名，另 58 个区域网格可切换显示）

L1  单据点灰盒（**点了才加载**）
    ├─ ① **130 个具名据点：内嵌进 HTML**（3.0 MB / 32,889 实体）
    │     ⇒ 把 world_map.html 单独拷到任何地方都能点开城镇，不依赖 town_data/
    ├─ ② 58 个区域网格：外部 town_data/<code>.js（`<script src>` 动态注入）
    └─ ③ 兜底：② 失败时弹出「选择 town_data 文件夹」按钮（input[webkitdirectory]，
          file:// 下 Directory Picker API 不可用），读完文件后重试
       按 archetype 包围盒建 InstancedMesh（1 个 draw call / 整个镇）
       ★ 切镇时先 disposeTown()（geometry / material / map 全释放）再建新的
       ★ 超过 24,000 个实体才抽样，正常镇不用抽样

L2  高清镇（可选，另行打开）
    └─ export/levels/town/town_textured.html（真 UV + 游戏原生贴图，Valentine 已做）
```

### 4.2 为什么这样就不卡

| 手段 | 效果 |
|---|---|
| 不把据点数据内联进 HTML | 主页只 2.1 MB（内联的话要几百 MB） |
| 每镇一个 `.js`，`<script src>` 懒加载 | `file://` 下也能用（classic script 不受 ES module / fetch 限制） |
| 同一时刻只保留 **1 个**据点几何 | 内存恒定，与"全世界有多少据点"无关 |
| 整镇用 **InstancedMesh** | 一个 draw call 画几千个盒子 |
| 切换前 `dispose()` 几何/材质/贴图 | 不会累积泄漏 |
| 实体数 > 24,000 才抽样 | 极端区域（如 `new`）也不爆 |
| WebGL 显存：只有 1 个 box geometry + 1 个 instanced buffer | 千级 MB → 几 MB |

### 4.3 交互（**已重做**，见 §7）

| 操作 | 作用 |
|---|---|
| **左键拖** | 绕目标点旋转（俯角被限制在 7°~73°，**永远不会贴地/钻到地图下面**） |
| **右键拖** / 中键拖 / **Shift+左键拖** | 沿屏幕平面平移 |
| **滚轮** | 朝光标缩放（光标下的点尽量不动） |
| **双击** | 把该点设为中心 |
| **↑ ↓ ← →** | 微调旋转；**+ / −** 缩放 |
| **双指**（触屏） | 捏合缩放 + 双指平移 |
| 视角预设 | 俯视 / 45° / 低空 / 重置 |
| 打开据点 | 显示实体总数、大结构/建筑/小物件分类、中心坐标、标高、范围，可「飞到镇中心 / 清除」 |

HUD 右上角实时显示 **方位角 · 俯角 · 视距**。

## 7. 操控重做（2026-10-16 修复，用户反馈"根本没法正常旋转"）

本轮修了 4 个真 bug，其中第 1 个就是"没法正常旋转"的根因：

| # | Bug | 后果 | 修法 |
|---|---|---|---|
| 1 | ★ **轨道球坐标写成了绕 Z 轴**（`ph=acos(off.z/r)`），但 three 是 **Y-up** | 左右拖拽不是绕竖直轴旋转，而是让地图**绕一根水平轴翻滚/翻跟头** —— 手感完全错乱，这正是"根本没法正常旋转" | 改成标准 **Y-up 球坐标**：`ph=acos(off.y/r)`、`th=atan2(off.z,off.x)`，`camera.y=target.y+r·cos(ph)` |
| 2 | ★ **`const GROUND = new THREE.Plane(...)` 写在模块顶层** | 模块求值时 three 还没 `await import` 完 ⇒ 抛异常 ⇒ `GROUND` 永远停在 TDZ ⇒ **滚轮缩放整个失效**（点了没反应） | 改成 `let GROUND=null`，在 `groundPoint()` 里首次使用时懒创建 |
| 3 | **极角没有上限** | 能一路拖到贴着地平线 ⇒ 地图变成一条"薄片"，看起来像坏了（用户截图就是这个状态） | 钳到 **俯角 7°~73°**，永不贴地、永不钻到地图下方；视距钳到 80~46000 m |
| 4 | 平移用 `(0,0,1)` 当 up、旋转按像素线性 | 平移方向诡异；旋转过灵敏（320px≈87°） | 平移改用相机自己的 `前/右` 基向量；旋转改按视口比例 |
| 5 | ★ **拖拽方向是"抓地图拖"（Google Maps 式）**，不是 **OrbitControls / Blender 式** | 左右、上下**两个方向都和习惯相反** | 逐字对齐 three.js `OrbitControls`：`θ-=dx·2π/h`、`φ-=dy·2π/h`，并把球坐标约定也换成它的 `θ=atan2(x,z)` / `φ=acos(y/r)` |

### 7.1 方向约定怎么定死的（做了 A/B 实测，不靠感觉）

拿项目里现成的 `export/levels/town/addons/controls/OrbitControls.js`（真实 three.js 官方实现）
起本地 http 服务跑了一次对照（`work/verify/orbit_ab.html`）：

```
初始相机 (-900, 10800, 9900)   →  拖右 360px（画布高 900）
真实 OrbitControls:  (-5091, 10800, -8538)
北方点在屏幕上的横坐标:  1046  →  -4058     ⇒ 内容向左走
```

⇒ **OrbitControls 确实就是"拖右 → 内容往左"**（镜头跟着鼠标绕物体转，而不是抓地图拖）。
本查看器已按它的公式实现，并**逐字对齐灵敏度**：两轴都用 `2π·像素 / 画布高`（画布高 900 时，拖 360px ≈ 144°）。

### 7.2 兜底：两个方向反转开关

HUD 里有 **「拖拽方向：左右反转 / 上下反转」** 两个按钮（`localStorage` 记忆），
默认 = OrbitControls 标准；点一下就切到自己顺手的方向，不用改代码。


顺带修的两处观感问题：

- **地图边缘"锯齿围栏"**：地形最外圈是硬边、顶点高度跳变 ⇒ 把最外 3 圈钳成第 3 圈的值，边缘变成干净平滑的线
- **区划多边形"垂直尖刺"**：越界顶点的 `heightAt` 被钳到边界值，与内侧顶点形成几十~几百米落差 ⇒ 渲染成尖刺（Guarma 正好压在南边界上）。修法：多边形顶点先**钳进地形范围**，并丢弃最长边 > 2600 m 的跨界拉丝三角

### 7.3 ★ 地形"黑块 / 边界对不上"的根因（2026-10-16 补修）

## 10. 安尼斯堡"布局乱"的定位与修复（2026-10-16）

### 10.1 先把"布局是不是错的"验证掉

把 L2 的 **163 个实例的世界空间包围盒**投影成平面轮廓，叠在官方底图（STATE 陆地 + 官方水体）上：

```
结果：密集、连贯的城镇轮廓（346×308 m），仅东南侧码头/栈桥伸进 Lannahechee 河 —— 那本来就该在水上
⇒ 位置数据是正确的，不是"布局乱"
```

### 10.2 真正的原因：**地形分辨率**

| 事实 | 数值 |
|---|---|
| 全局地形网格 | 1024² 顶点 / 12.3 km ⇒ **12 m/格** |
| 用户出问题时的视距 | **292 m** |
| 建筑 z 均值 vs 镇中心地形 | 55.7 m vs 59.0 m（平均只差 3.3 m）|
| 但 12 m/格 ⇒ 局部高度误差可达 | **±12 m**（建筑就会显得浮起或埋进地里）|

近距离下 12 m/格的地面本身就是马赛克，叠加底图 6 m/px 的模糊水色 ⇒ 观感"乱七八糟"。

### 10.3 修法：开镇时切 **4 m 精地形**

- 构建时为每个 L2 据点烘一张 **±500 m / 4 m 的局部高程补丁**（251²，内嵌进 `l2/<code>.js`，仅 **150 KB**）
- 打开据点后 `refineTerrain()`：把落在补丁范围内的地形 chunk **顶点高度按 4 m 数据重算**
  （几何仍是 12 m 网格 ⇒ 不会有 z-fighting，也不需要隐藏全局地形）
- 关镇 / 切镇时 `HPATCH=null; refineTerrain()` 还原

这样建筑与地面的相对高度误差从 ±12 m 降到 ±2 m 量级。

### 10.4 顺带修的真 bug

`insts` 的缩放写成 `[sxy, sz, sz]`，应为 **`[sxy, sxy, sz]`**（RDR2 的 XY 是水平面）。
安尼斯堡所有实体的缩放都是 1，所以没暴露；但对后续有缩放的据点会造成 Y 方向拉伸。已修（`export_town_l2.py`）。

### 10.5 「地编数据不全」—— 你说对了一半

| 数据 | 状态 |
|---|---|
| L2 真模型（163 实例 / 162 模型） | ✅ 完整可用，构成连贯城镇 |
| `ann_*.ymap` 的 **632 个实体**（**629 个不同 archetype**） | ❌ 解不出模型名 |

对这 632 个实体做过穷举排查，全部失败：
1. `joaat(ydr 名)` 直接匹配 → 4/632
2. 名字变体（大写 / 去下划线 / 加 `.ydr` / `ann_0→ann0`）→ 16/632
3. archetype 包围盒 ↔ ydr 自身包围盒（`buildings_jklm` + `buildings` + 本区共 1713 个 ydr）→ **13/160**
4. 反查 1026 个 ytyp 里 +88/+112 的哈希 → 0 命中

**判断**：632 个实体对应 629 个互不相同的 archetype（几乎一实体一 archetype），且尺寸高度各异 ——
这更像 **LOD / 流式占位表**，而不是主摆放表。主摆放表是那些**哈希命名的 ymap**
（`0xB653434` 61 个、`0x4B62F41A` 30 个、`0x5665C20D` 25 个…），我们已经全部用上。

⇒ 结论：**真摆放没漏**；漏的是那 632 个占位实体对应的（我们没抽到的）模型 ——
若要补齐，需要再解一层「archetype 定义 → drawable 名」的映射（社区工具如 CodeX/Sollumz 走的也是这条路）。

## 11. 安尼斯堡：两个问题的定量定位与修复（2026-10-16）

### 11.1 「建筑陷入地形」

**先纠正评价指标**：一开始我拿"模型底部 z − 地面"当指标，是**错的** ——
坡道/挡墙/桩/埋入地基这些模型**本来就应该伸到地面以下**（实测 `ann01_mine_blockade_dslod` 局部 zmin = −20 m）。
正确的指标是 **实体原点 z − 地面**。

| 指标（实体原点 − 地面） | 中位 | 均值 | std | <2 m |
|---|---|---|---|---|
| 修正前（原始 4 m 全局地形） | +0.77 | +1.33 | 4.00 | 54% |
| 修正后（底座校准场 IDW） | **−0.33** | **−0.10** | **3.28** | **58%** |

**两个成因**：

1. **城镇脚下没有地形 patch**（被建筑取代）⇒ 我们的 4 m 高程图在镇区是插值补的，与真实地面有系统偏差。
   修法：**用建筑底座推局部校准场**（本项目笔记 §0.6 #18 早记过）——
   残余场 = `实体 z − 该点原始地形`，用 **IDW 反距离加权** 重建（试过"扩散+大核平滑"，会把稀疏样本的修正量稀释掉，反而变差），
   离样本 >150 m 处指数衰减归零；最终 `Z = 地形大形 + 加权残余`（不抹平地形起伏）。
   补丁 184²@4 m，内嵌进 `l2/<code>.js`，仅 **82 KB**。

2. **地形网格太粗**：默认 768² ⇒ **16 m/格**，粗三角形会直接**切进建筑**（视觉上就是"陷进地里"）。
   修法：开镇时把落进补丁范围的地形块 **细分 3 倍**（16 m → 5.3 m），并用 `groundZ()`（4 m 精地形 + 校准场）重算顶点；
   关镇时还原原几何。

### 11.2 「建筑不全」—— 查下来是**误判**，但确实修掉了一类重复

**证据 1：顶点密度图**。把 L2 的 186 万顶点投影成密度图，得到的是**结构完整的主街 + 两侧建筑 + 栈道 + 码头 + 铁路**；
而同尺寸画 `ann_*.ymap` 那 632 个实体，反而是**稀疏零散的点云**。

**证据 2：距离分析**。632 个实体里 >10 m 的有 240 个，它们到最近 L2 实例的**距离中位只有 4.7 m**（>15 m 的仅 17 个）——
说明 L2 的位置**已经覆盖**了这些实体的位置，它们是同一批东西的不同 LOD。

⇒ 那 632 个实体（**629 个互不相同的 archetype**、几乎一实体一 archetype）判断为 **LOD/流式占位表**，
主摆放表是那些哈希命名的 ymap，已全部用上。

**顺带修掉的真问题**：同位置的**表现层变体重复**。
`_em_hd`(自发光) / `_d`(细节) / `_dc`(贴花) / `_det_dec` 是**同一栋楼**按距离切换用的层，
我们原来全画了 ⇒ 墙体互相重叠 + z-fighting ⇒ **看起来又乱又"碎"**。
去重规则：按「位置 + 基名」分组，组内优先留基名（不能按位置一刀切 —— `ann_05_conv06b` 与 `ann_05_conv06b_support`
是同位置的**合法不同部件**，`ann_boardwalk_01` 与 `ann_pie_02_dockside1_d` 也是）。安尼斯堡 177 → 165 实例，丢 12 个真重复。

**用户实测报错**：`RENDER ERR: TypeError: Cannot read properties of null (reading 'has') at updateL2Chunks`

**根因**：`L2TEX` 在 `ensureL2Shared()` 里先被赋值，而 `l2Loaded/l2Missing/L2CHUNKS`
是在它的 `.then()` 回调里才初始化 ⇒ 中间那几帧 `animate` 调 `updateL2Chunks()` 时 `l2Loaded` 还是 null ⇒
每帧抛异常，把整个渲染循环打挂（画面全黑）。

**修法**：`L2TEX` 一赋值就 `l2Loaded=l2Loaded||new Set()` 等；`updateL2Chunks` 加 `!l2Loaded || !L2CHUNKS` 防御；
渲染异常改成"只提示一次"不再整帧中断。

**同轮另外修的两处**：
1. **取景中心错误**：`sdn` 组只有 103 个实体、范围仅 **29×102 m**，相机飞到错的地方。
   改为用**官方 zone 包围盒**覆盖（`sdn → StDenis`，862×955 m），
   同时给 val/ann/rho/arm/tum 等 12 个据点都加了同样的修正。
2. **分块改成串行加载**（`pumpChunks` 队列）：近的块先出画面，内存平缓增长，
   而不是 13 块并发解析 200 MB。
